## เดโมสำหรับนำเสนอ

**เข้าระบบ** มีสองโหมด แล้วแต่ว่า build/เครื่องนั้นมีกุญแจ Supabase หรือเปล่า (ดู `lib/cloud.ts → cloudEnabled`)

| โหมด | ใช้เมื่อไหร่ | การเข้าระบบ |
|---|---|---|
| local / เดโม / GitHub Pages / ไฟล์แชร์ | นำเสนอ ลองฟีเจอร์ | เลือกบทบาทแล้วเข้าเลย — **ล็อกอินปลอม** ไม่แตะเซิร์ฟเวอร์ (ปุ่มหน้าตาเหมือน "เข้าสู่ระบบด้วย Google" บนเดโมไม่ได้ไปหา Google จริง) |
| cloud (เว็บนำร่อง) | ใช้กับเซิร์ฟเวอร์จริง | **ปุ่ม Google เป็นทางหลัก** (Supabase OAuth) · อีเมล+รหัสผ่านเป็นทางสำรอง · ใครเข้าได้ตัดสินที่รายชื่อเชิญบนฐานข้อมูล (`0009`) |

ใครเข้าได้: อาจารย์ = อีเมลในแท็บอาจารย์ของหน้า "รายชื่อ & นำเข้า" (หรือ `supabase/add-teacher.sql`) · นักศึกษา = อีเมลในรายชื่อ หรือล็อกอิน
@student.mahidol.edu แล้วใส่รหัสนักศึกษาผูกเอง → อาจารย์ที่ปรึกษายืนยัน (`0023`) · ยังไม่ได้ต่อ SSO ของมหาวิทยาลัย

**สลับบทบาทระหว่างเดโมโดยไม่ต้อง logout** — แถบ DEMO ด้านบน (จอกว้าง) หรือปุ่มลอยมุมจอ (`RoleFab` · มือถือ/iPad)
ในโหมด cloud สลับได้เฉพาะบัญชีที่เป็นทั้งนักศึกษาและอาจารย์

**รีเซ็ตข้อมูลกลับสถานะเริ่มต้น** (ก่อนเริ่มเดโมรอบใหม่): แถบ DEMO → **รีเซ็ตข้อมูล** หรือหน้า sync (กระดิ่งมุมขวาบนของหน้าแรก) → **รีเซ็ตข้อมูล** — มีเฉพาะโหมดเดโม

**ลำดับที่แนะนำสำหรับ 5 นาที**
1. หน้าแรก → กด "ผ่าน Step" → bottom sheet → ยืนยัน → toast + ปุ่มเลิกทำ (แสดงว่ากดผิดแก้ได้)
2. หน้า sync → เปิดโหมดออฟไลน์ → กลับหน้าแรก → กดผ่าน step อีกครั้ง → ยังสำเร็จทันที + ป้าย "รอ sync"
3. กลับหน้า sync → เห็นคิว → ปิดออฟไลน์ → กด sync ทันที
4. คนไข้ → เปิดเคส → timeline 0–10 พร้อม checklist และ badge "ทำเอง"
5. เกณฑ์ → เกณฑ์สะสม 2 ปี (CD/RPD/Crown+Post-core/Recall) และเกณฑ์รายปีแยกกันคนละการ์ด
6. คาบ → เช็คอินรายคาบ → ท้ายแท็บมีลิงก์ส่งออก → หน้ารายงาน A4 มีช่องลงนาม → ปุ่มสร้าง PDF / CSV
7. สลับเป็นอาจารย์ → เมนูซ้าย: **สรุปกลุ่ม · ประเมินรายคาบ · แผนการรักษา · ความรู้และทักษะ · การสอบ · ประเมินตนเอง** (กลุ่มที่ดูแล)
   และ **ภาพรวม · วิเคราะห์รวม · รุ่นที่จบแล้ว · ตั้งค่า · รายชื่อ & นำเข้า** (ทั้งชั้นปี · สองหน้าหลังเฉพาะหัวหน้ารายวิชาบางส่วน)
8. อาจารย์ → ประเมินรายคาบ (ให้คะแนน 8 หัวข้อ → บันทึกผล · ลงนาม) → ตั้งค่า แก้เกณฑ์ แล้วกลับไปดูหน้านักศึกษา ตัวเลขเปลี่ยนตามทันที

## กติกาที่ implement ไว้แล้ว

1. **Upper/lower เป็นคู่** — `pairId` + `acceptedDate` เดียวกัน แต่ `procIndex` แยกกันเด็ดขาด
2. **% completed** = `(progression + 1) / (maxProgression + 1)` ตรงกับคอลัมน์ `% Completed` ในชีต
3. **เกณฑ์ขั้นต่ำ (แก้ล่าสุด 10 ก.ย. 2026)** — สะสม 2 ปี: CD 2 (นับต่อ arch) · RPD 2 · Crown/Bridge 2 โดยในนั้นต้องเป็น Post-core อย่างน้อย 1
   (Post-core นับรวมอยู่ในโควตา Crown ไม่ได้แยก) · **Recall Removable (CD/RPD) 1** · **Recall Fixed (FDP) 1**
   รวมเป็น 8 เคส **บวกเงื่อนไขรายปี**: ทุกปีการศึกษาต้องจบอย่างน้อย 3 ชิ้นงาน
   นับเมื่อชิ้นงานจบเคสและ `minimumRequirement === true`
   · **Simple APD ไม่นับทั้งสองเกณฑ์**
   · **Recall นับเฉพาะเกณฑ์สะสม ไม่นับเกณฑ์รายปี** — เกณฑ์รายปีคือ "ปีนี้จบเคสใหม่กี่ชิ้น"
     ซึ่ง recall ไม่ใช่การรับเคสใหม่ (ถ้าภาคขอให้นับด้วย มีสวิตช์ `perYearCountsAllTypes` อยู่แล้ว)
   · โค้ดแยกสองชุดไว้ที่ `domain/catalog.ts`: `CUM_REQ_TYPES` (สะสม) กับ `REQ_TYPES` (รายปี)
   อาจารย์แก้ค่าทั้งหมดได้จากหน้า "ตั้งค่า"
4. **ลำดับการแสดงรายการ** — minimum requirement ก่อน → CD → RPD → APD → Post-core → Crown/Bridge → Recall Rem. → Recall Fixed และผู้ป่วยคนเดียวกันอยู่ติดกัน
5. **เคสค้าง** — ไม่อัปเดตเกิน N วัน (ตั้งได้ 7/14/21/30) flag ทั้งสองฝั่ง
6. ~~รอบส่งรายงาน~~ — **ถอดออกแล้ว** (ส.ค. 2569) แทนด้วยเช็คอินรายคาบ · `rounds.ts` ลบทิ้งแล้ว
7. **Export** — PDF ที่มีช่องลงนาม (`window.print()`) และ CSV ตามคอลัมน์ชีตเดิม
8. **Self-performed (`*`)** — เก็บลง `ProgressUpdate.selfPerformed` และมี badge "ทำเอง" ใน UI
9. **Offline-first** — เขียนลง IndexedDB ทันที เข้าคิว แล้ว sync เมื่อออนไลน์
10. **เลิกทำ** — บันทึกเป็น reversal ใน `ProgressUpdate` ไม่ลบประวัติ
11. **Audit log** — ทุกการเปลี่ยน step / อนุมัติ / สร้างชิ้นงาน
12. **Catalog versioning** — ทุกชิ้นงานเก็บ `catalogVersion` (`DTPT502-2569`)
13. **ชนิดชิ้นงานถอดได้ตามชีต** — CD / Complicated APD / Complicated RPD / Simple RPD / Simple APD พร้อมวงเล็บบอกจำนวนฟันที่เหลือ (`domain/catalog.ts → DENTURE_CLASSES`)
14. **Count CDA** — คำนวณอัตโนมัติจากจำนวน arch ที่เป็น CD หรืองาน Complicated แสดงในแท็บ Case CD ของ dashboard
15. **สถานะ “ยังไม่เข้าเกณฑ์ · รอตรวจ”** — ชิ้นงานที่อาจารย์ยังไม่ตรวจรับ จะไม่ถูกนับเข้าเกณฑ์ อาจารย์กดตรวจรับได้จากหน้าตรวจงาน
16. **รายงาน A4 มีช่องติ๊ก 0–10** ครบ 11 ช่องเหมือนชีต · CSV เรียงคอลัมน์ตรงกับ tab PTn รวม Sect II (แยก Removable/Fixed) และวันที่บันทึกข้อมูล
17. ~~ตารางส่งรายงาน 7 รอบ~~ — **ถอดออกพร้อมระบบรายงาน**
18. **กดเลข step 0–10 ที่ไหนก็ได้เพื่อดูว่าข้างในมี procedure อะไร** — กราฟคอขวด (ทั้งหน้าภาพรวมและหน้าวิเคราะห์)
    และ timeline ของนักศึกษา · เลือก "ทุกประเภท" จะเทียบให้เห็นว่า step เดียวกันหมายถึงคนละขั้นตอนในแต่ละประเภทงาน
    (`components/StepInfo.tsx`)
19. **การแสดงผลเลือกตามขนาดข้อมูลจริง** — เกณฑ์เป็นหลักหน่วย (CD 2 · RPD 2 · Crown 2 · ปีละ 3)

## คิวส่งขึ้นตู้กลางจำ "ช่องที่แก้" ไม่ใช่แค่ "แถวที่แก้"

เจอ 12 ก.ย. 69 ด้วย `npm run test:clinic` (จำลองคาบจริง ไม่ใช่การอ่านโค้ด) · แก้ 13 ก.ย. 69

**อาการ:** คิวเดิมเก็บแค่คีย์ของแถวที่แก้ ตอนส่งจริงอ่านแถวล่าสุดจากเครื่องแล้ว upsert
**ทั้งแถว** — เครื่องที่ถือฉบับเก่าของช่องที่ตัวเองไม่ได้แตะ จึงเขียนค่าเก่านั้นทับของใหม่
นักศึกษาเปิดมือถือ + ไอแพดค้างทั้งคู่ · กด step บนไอแพด แล้วพิมพ์โน้ตบนมือถือ
→ step หายไปโดยไม่มี error ไม่มีป้าย

**ที่แก้:** middleware อ่านฉบับเดิมด้วย `getMany` ก่อนเขียน แล้วจดว่าต่างช่องไหน
ตอนส่งจึง PATCH เฉพาะคอลัมน์นั้น · แถวใหม่ยังส่งทั้งแถว (PATCH สร้างแถวไม่ได้)

| กันอะไร | ที่ไหน |
| --- | --- |
| เครื่องเดียวกันของคนเดียวกันทับกันเอง | คิวรายช่อง (`data/cloudSync.ts`) |
| อาจารย์ทับโน้ต/กิจกรรมของนักศึกษา | `0020` — กฎที่ฐานข้อมูล กันการยิง API ตรงได้ด้วย |
| นักศึกษาทับคะแนนของอาจารย์ | `0017` (เดิม) |

**สี่กับดักที่ล็อกไว้ในเทสต์แล้ว**

1. `dirty` ชั้นในเป็น `Map` แล้ว — ตัว `skip` ของ `pullAll` ต้องใช้ `.keys()`
   ถ้า spread ทั้ง Map จะได้คู่ `[pk, ช่อง]` แล้ว skip ไม่ตรง pk → pull ทับแถวที่ยังค้างส่ง
2. **PATCH ที่ไม่โดนแถวไหนเลย** = ตู้กลางไม่มีแถวนั้น (ใครลบไป) ต้อง fallback ไปสร้างใหม่
   ไม่ใช่ถือว่าสำเร็จ — ข้อเสียนี้ upsert ไม่มี จึงต้องเช็คทุกครั้ง (`test:clinic` ข้อ ⑪)
3. สำเนาคิวบนดิสก์เป็น `v: 2` แต่ **ต้องอ่านรูปเก่าได้ด้วย** เพราะคนที่อัปเดตแอปกลางคาบ
   มีสำเนารุ่นเก่าค้างในเครื่อง — อ่านไม่ออกคืองานที่ทำตอนออฟไลน์หายหมด (`test:offline`)

4. **เน็ตหลุดไม่ใช่ "ตู้ปฏิเสธ"** — ของที่ส่งไม่ขึ้นจะถูก "กัก" ให้ผู้ใช้เห็นก็ต่อเมื่อตู้ตอบรหัส
   ปฏิเสธมาจริง (`isRefusal`) · error ที่ไม่มีรหัส = ส่งไม่ถึง → รอส่งต่อไปเรื่อยๆ
   เจอ 13 ก.ย. 69: เดิมนับรวมกัน ไวไฟห้องคลินิกหลุดครึ่งนาทีก็พอให้เคสใหม่ถูกกักแล้วไม่ขึ้นตู้เลย
   และ pull ไม่ได้ข้ามแถวที่ถูกกัก จึงทับงานที่ยังไม่ได้ส่ง — แก้ทั้งสองข้อแล้ว

ตรวจกับ Dexie ตัวจริงในโหมด cloud แล้วว่า `await getMany` ข้างใน `rw` transaction
หลายตารางไม่ทำให้ transaction พัง (รวมถึง `Dexie update()` ที่อ่าน-แก้-เขียนข้างในตัวเอง)

## ทดสอบหน้าจอจริงในโหมด cloud โดยไม่แตะเซิร์ฟเวอร์จริง

`scripts/local-supabase.mts` คือ Supabase จำลองที่ข้างในเป็น **Postgres ตัวจริง** (PGlite)
รัน migration ทุกไฟล์ · กฎ RLS / trigger / สิทธิ์ของจริงทุกบรรทัด · รับคำขอแบบเดียวกับ Supabase

### ตัวกู้ข้อมูลมีสามขั้น — ขั้นแรกปลอดภัยเสมอ

| คำสั่ง | ทำอะไร | แตะเซิร์ฟเวอร์ไหม |
| --- | --- | --- |
| `npm run restore` | ตรวจว่าสำเนาชุดล่าสุดกู้ได้จริงไหม | ไม่ |

### สามเรื่องที่การกู้ข้อมูลไม่ใช่แค่ "ยัดแถวกลับ"

1. **ห้ามใช้ service key กู้ข้อมูล** — trigger `checkin_scoring_guard` (`0017`) เช็ค `is_teacher()`
   จาก `auth.uid()` ซึ่ง service key ไม่มี → นับเป็น "ไม่ใช่อาจารย์" → ตอน insert ถูกปฏิเสธ
   และตอน update จะ**คงค่าเดิมไว้เงียบ ๆ** คือคะแนนของทุกคาบหายโดยไม่มี error
   `restore.ts` จึงปฏิเสธ service key และหยุดถ้าบัญชีที่ล็อกอินไม่ใช่อาจารย์
2. **`audit` เขียนซ้ำไม่ได้** — trigger `audit_no_change` (`0009`) ห้าม update/delete
   ต้องยิงแบบ ignore-duplicates · และ `audit_stamp` จะประทับ `actor_uid` เป็น**คนที่กู้**
3. **กู้เข้าโปรเจกต์ว่างเปล่าไม่ได้ทันที** — `app_users.uid` อ้าง `auth.users` และ `is_teacher()`
   ก็อ่านจาก `app_users` · ลำดับที่ใช้ได้: สร้างบัญชีอาจารย์ในหน้า Authentication →
   เพิ่มแถว `teachers` + `app_users` ด้วย SQL → แล้วค่อยกู้ที่เหลือ

`updated_at` ของทุกแถวจะกลายเป็นเวลาที่กู้ (trigger `zz_touch_updated_at`) — ไม่ใช่บั๊ก
และจำเป็น เพราะเครื่องของนักศึกษาดูค่านี้เพื่อรู้ว่าต้องดึงอะไรลงใหม่

ตารางกลาง (อาจารย์ · กลุ่ม · ค่าตั้ง · นโยบาย · รายชื่อเชิญ) ไม่แตะเลย

### ไฟล์รูปต้องใช้กุญแจแยก

กฎบักเก็ต (`0018`) ให้นักศึกษาเจ้าของโฟลเดอร์อัปรูปได้คนเดียว บัญชีอาจารย์ที่ใช้กู้ตารางจึงคืนไฟล์รูปไม่ได้

**เจอจากการซ้อมกู้ครบวงจรครั้งแรก (13 ก.ย. 69) — สามเรื่องที่ทำให้กู้รูปไม่ได้มาตั้งแต่แรก:**
ไม่ได้บอกชนิดไฟล์ (บักเก็ตรับเฉพาะ JPEG → ปฏิเสธทุกใบ) · ตาราง `photos` ไม่อยู่ในแผนกู้เลย

### ① ปิดบังชื่อ/HN — ต่อเข้าหน้าจอแล้ว

`src/lib/privacy.ts` — `caseCode()` · `maskedName()` · `maskedHn()` · `patientLabel(p, level)`
รหัสเคสคำนวณจาก id ภายในของผู้ป่วย **ไม่ใช่จาก HN** — ถ้าคำนวณจาก HN คนที่รู้ HN ของคนไข้คนหนึ่ง
จะไล่เดาได้ว่าแถวไหนคือคนนั้น (HN เป็นเลขไม่กี่หลัก ทำตารางเทียบได้ในไม่กี่นาที)

⚠️ รหัสเคส **ไม่ใช่ข้อมูลนิรนาม** — มันคือนามแฝง ยังนับเป็นข้อมูลส่วนบุคคลตาม PDPA
ประโยชน์คือลดจำนวนคนที่เห็นชื่อจริงลงเหลือเท่าที่จำเป็น ไม่ใช่ทำให้ข้อมูลหลุดกรอบกฎหมาย

ใช้กับ: หน้าจอ (ระดับรายหน้าตาม `identityLevelFor` · หน้าประเมินรายคาบเห็น `ผ. A. (HN ••••••)`) · ไฟล์ที่ส่งออกแบบปิดบัง · ชื่อไฟล์รูป · ข้อความใน audit log (ดูข้อ ④)

### ② Retention — ลบจริงสองฝั่ง

- ฝั่งเซิร์ฟเวอร์: RPC `purge_expired_cohorts('ลบถาวร')` — ลบ 11 ตารางในธุรกรรมเดียว
  ต้องผ่านสองด่าน: คนสั่งเป็นหัวหน้ารายวิชา **และ** `retention_enabled = true`
- ฝั่งเครื่อง: `repo.ts → purgeExpiredCohorts` ลบ IndexedDB ของเครื่องที่กดปุ่ม

**ลำดับสำคัญ**: เซิร์ฟเวอร์ก่อน เครื่องทีหลัง — ถ้าทำกลับกันแล้วเซิร์ฟเวอร์ปฏิเสธ
เครื่องนี้จะว่างแต่ตู้กลางยังเต็ม แล้ว `pullAll` รอบถัดไปดึงกลับลงมาหมด
ผู้ใช้จะเห็นว่า "ลบแล้วมันกลับมา" โดยไม่รู้สาเหตุ

ทำไมพึ่งคิว sync อย่างเดียวไม่พอ — คิวลบได้เฉพาะแถวที่มีอยู่ในเครื่องนั้น และล้มเหลวแบบเงียบได้ 4 ทาง
(เหตุผลเต็มอยู่ในหัวข้อ ⑥ ของ `0016_pdpa.sql`)

**คนที่ไม่มี `entryYear` จะไม่ถูกลบเลย** — เดารุ่นแล้วลบผิดคนคือความเสียหายที่กู้ไม่ได้
หน้าตั้งค่าขึ้นตัวเลขให้เห็นว่ามีค้างกี่คน ต้องไปเติมรุ่นในหน้ารายชื่อก่อน

### ③ สิทธิ์ export

ทุกทางออกผ่านด่าน `authorizeExport()` ตัวเดียว (CSV · ปุ่มสร้าง PDF · ปุ่มสำรองข้อมูลในแอป) ซึ่งทำตามลำดับ: ตรวจสิทธิ์ → จด audit ที่เซิร์ฟเวอร์ → ค่อยสร้างไฟล์

⚠️ **ขอบเขตที่ทำได้จริง** — นี่คือการคุม "ปุ่มในแอป" ไม่ใช่การคุม "การเอาข้อมูลออก" ทั้งหมด

### ④ audit log ที่แก้ไม่ได้ — มีอยู่แล้วก่อนงานรอบนี้

## ค้างให้ภาควิชา/คณะตัดสิน (PDPA)

เรียงตามลำดับที่ควรถาม — ข้อ 1–3 บล็อกการรับข้อมูลจริง

1. **ระยะเวลาเก็บที่แน่นอน** — ตอนนี้ค่าตั้งต้นคือ 5 รุ่น จาก "ประมาณ 5 ปี" ที่อาจารย์เคยพูด
   ต้องได้ตัวเลขที่เป็นมติ + **นับจากอะไร** (จบการศึกษา? ปิดเคสสุดท้าย? ปีการศึกษาที่รับเข้า?)
   ตอนนี้โค้ดนับจากปีที่ขึ้นคลินิกปีแรก (`entryYear`)
2. **ใบยินยอมผู้ป่วย** — ยังไม่มีเลยในระบบ ทั้งข้อความและช่องเก็บสถานะ
   ต้องรู้ก่อนว่าใครเป็นผู้ควบคุมข้อมูล (คณะ? โรงพยาบาลทันตกรรม?) และใบยินยอมเดิมของคลินิก
   ครอบคลุมการเก็บในระบบนี้อยู่แล้วหรือต้องขอใหม่
3. **ข้อมูลอยู่เซิร์ฟเวอร์สิงคโปร์** — Supabase region ที่ใช้อยู่ไม่ได้อยู่ในไทย
   ต้องให้คณะรับทราบและตัดสิน: ยอมรับได้ / ย้าย region / ย้ายไปเซิร์ฟเวอร์มหาวิทยาลัย
   (ย้าย region = สร้างโปรเจกต์ใหม่แล้วกู้สำเนาเข้าด้วย `restore.ts` + `RESTORE_URL` — ตอนนี้มีข้อมูลจริงแล้ว ต้องนัดวันหยุดใช้และย้ายทั้งก้อน)
4. **หน้าไหนควรเห็นชื่อ/HN บ้าง** — **ผู้ใช้ตัดสินแล้ว 11 ก.ย. 69: เปิดปิดบังชื่อ**
   หน้าประเมินรายคาบเห็นแค่รหัสเคส + ชื่อย่อ + HN ปิดบัง (`ผ. A. (HN ••••••)`)
   ส่วนใบพิมพ์ Section II/III ที่ต้องเซ็นยังเห็นชื่อจริง เพราะชื่อคือเนื้อหาของเอกสารนั้น
   ตารางตัดสินอยู่ใน `lib/privacy.ts → identityLevelFor` (ยืนยันด้วยการกดจริง 13 ก.ย. 69)
5. **audit log เก็บนานแค่ไหน** — ตอนนี้ลบไม่ได้เลยโดยตั้งใจ (เป็นหลักฐาน)
   แต่แถว audit มี **ชื่อนักศึกษา** อยู่ ซึ่งขัดกับ retention ของนักศึกษาเอง
   ถ้าภาคต้องการให้ลบตามไปด้วย ต้องแก้ trigger ใน `0009` — **ยังไม่ทำ** เพราะเป็นการลดความเข้มของสิ่งที่ตั้งใจทำไว้
6. **รูปผู้ป่วย** — ขึ้น storage กลางแล้ว (`0018`) และอยู่ในขอบเขต retention เดียวกับข้อมูลอื่น:
   `photos` มี trigger `photos_cleanup_object` ที่ลบแถวใน `storage.objects` ตามทุกครั้งที่แถวหาย
   ซึ่งครอบทั้งการลบชิ้นงาน ลบนักศึกษา และ `purge_expired_cohorts` ของ `0016`
   ⚠️ ข้อจำกัดที่ยังเหลือ: ลบแถวใน `storage.objects` ด้วย SQL ทำให้ metadata สะอาด แต่ไบต์ใน S3 อาจค้าง
   ตัวลบไบต์จริงคือฝั่งแอป (`photoStore.removePhotoFiles`) ซึ่งทำงานตอนผู้ใช้ลบผ่านหน้าจอ
   ถ้าลบฝั่งเซิร์ฟเวอร์ล้วน ควรรันคำสั่งหาไฟล์กำพร้าท้ายไฟล์ `0018` เป็นระยะ
7. **สิทธิ์ผู้ป่วยตาม PDPA** — ขอดู/ขอแก้/ขอลบข้อมูลตัวเอง ระบบยังไม่มีทางทำเลย
   (ตอนนี้ผู้ป่วยไม่มีบัญชี และไม่มีหน้าให้ภาคค้นแล้วลบรายคน)
8. **ผู้ประมวลผลข้อมูล** — Supabase เป็น data processor ต้องมีสัญญา (DPA) หรือไม่ ตามที่คณะกำหนด
9. **บัญชีล็อกอินของรุ่นที่ถูกลบตามกำหนดเก็บ** — `purge_expired_cohorts` ลบข้อมูลครบทุกตาราง
   และตั้งแต่ `0019` ลบรายชื่อเชิญ (`invites`) ให้ด้วย แต่ **ไม่ลบบัญชีใน `auth.users`**
   ซึ่งเก็บอีเมลของนักศึกษาไว้ · ตั้งใจไม่ลบจาก SQL เพราะเป็นการกระทำที่ย้อนไม่ได้และกระทบ
   ระบบล็อกอิน ควรเป็นขั้นที่คนกดเอง — ฟังก์ชันจึงคืนรายการอีเมลที่เหลือมาในช่อง
   `accounts_left` และ `audit-data.sql` บล็อก ⑥ ก็ลิสต์ให้ดูได้ทุกเมื่อ
   ต้องเคาะว่า **ใครมีหน้าที่ไปกดลบใน Authentication → Users และภายในกี่วัน**
10. **ช่อง "หมายเหตุ / สถานะผู้ป่วย" ในไฟล์ที่ส่งออกแบบปิดบัง** — ตอนนี้ส่งออกตามที่พิมพ์ทุกตัวอักษร
   ช่องนี้เป็นข้อความอิสระที่นักศึกษาพิมพ์เอง ถ้าใครเผลอพิมพ์ชื่อหรือ HN ลงไป
   ไฟล์ที่ "ปิดบังแล้ว" ก็ยังมีชื่อคนไข้อยู่ดี (ชื่อกับ HN ในช่องของมันเองถูกปิดบังถูกต้องแล้ว —
   ตรวจด้วย `npm run test:export`) · ทางเลือกคือ ตัดช่องนี้ออกจากไฟล์ปิดบัง / ให้อาจารย์ตรวจก่อนส่ง /
   ปล่อยไว้แล้วสอนตอนอบรม — เป็นเรื่องนโยบาย ไม่ใช่เรื่องโค้ด จึงยังไม่ตัดสินใจแทน

11. **รหัสเคสของผู้ป่วยที่นำเข้าจากชีต คำนวณย้อนได้จาก HN** — **ตัดสินใจแล้ว: ยอมรับ ไม่แก้**
    (ไม่เพิ่มค่าสุ่มลับ) · บันทึกไว้เพื่อไม่ให้ใครมา "แก้" ทีหลังโดยไม่รู้ว่าเป็นการตัดสินใจ
    `sheetImport.patientId()` = `p-imp-<hash(รหัสนักศึกษา|HN)>` และ hash เป็น FNV-1a ธรรมดา
    ไม่มีความลับในสูตร ใครที่รู้รหัสนักศึกษา (รู้กันทั้งภาค) แล้วไล่เดา HN สร้างตารางเทียบ
    HN → รหัสเคส ได้เอง · ผู้ป่วยที่ชีตไม่ได้กรอก HN (**35 จาก 209 คนในชีตจริงของรุ่น 55**)
    id ตกไปคำนวณจาก "ชื่อ" แทน
    เหตุผลที่ยอมรับได้: รหัสเคสมีไว้ลดการเห็นชื่อ/HN บนหน้าจอและในไฟล์ ไม่ใช่กันคนที่มี
    ฐานข้อมูลอยู่ในมืออยู่แล้ว · คนที่ไล่เดา HN ได้คืออาจารย์ในภาคซึ่งมีสิทธิ์เห็นของจริงอยู่แล้ว
    **กฎที่ต้องรักษาแทน: ห้ามเอา HN หรือชื่อผู้ป่วยไปใส่ข้อความ audit log** (แถว audit ลบไม่ได้)
    ถ้าวันหน้าภาคขอให้ปิดบังจริงจัง ทางแก้คือใส่ค่าสุ่มลับของภาคใน `app_settings`
    แต่เซิร์ฟเวอร์นำร่องมีข้อมูลจริงแล้ว — **เปลี่ยนสูตรตอนนี้ = ต้องเขียน migration ย้าย id ผู้ป่วยทั้งระบบ**
    (ทุกตารางที่อ้าง `patient_id` + รหัสเคสในไฟล์ที่เคยส่งออกจะไม่ตรงกับของใหม่) ไม่ใช่แค่แก้ฟังก์ชัน

## ระบบเช็คอินรายคาบ (เพิ่ม 26 ส.ค. 2026 — แทนระบบรายงานเดิม)

ถอดจากสมุดจริง "Clinical Performance Portfolio · Clinical rotation assessment logbook":

  Oral examination · Primary impression · Final impression · Bite registration · Tooth preparation · Laboratory work · Try in / Delivery ·
  ปรับแก้หลังใส่งาน · Recall · ส่งงาน · ตรวจงานกับอาจารย์ · ไม่มีผู้ป่วย — เก็บลงฐานข้อมูลเป็นข้อความตามนี้) ·
  ผู้ป่วยที่นัด · โน้ต — หน้าแรกมีแบนเนอร์เตือนถ้าวันนี้ยังไม่เช็คอิน
- **อาจารย์** (เมนู "ประเมินรายคาบ"): คิวคาบที่รอประเมิน แยกกลุ่ม — ให้คะแนน 0–3 ทั้ง 8 หัวข้อตาม Part B ของสมุด
  (Knowledge, Skill, Universal Precaution, Instrument Prep, Time Management, Chart Recording, Communication,
  General Conduct) → "บันทึกผล · ลงนาม" เทียบเท่าเซ็นสมุด นักศึกษาเห็นคะแนนทันที
- ระบบรายงาน (S5 + ตารางส่งรายงาน + การ์ดรอบ deadline) ถูกถอดออกทั้งหมด · หน้า export PDF/CSV ยังอยู่ (ลิงก์ท้ายแท็บ "คาบ")
- **รอทำต่อ**: แบบประเมินรวมต่อเคสแยกตามประเภทงาน (Assessment form for Removable prosthesis case ฯลฯ) — ผู้ใช้จะส่งฟอร์มของประเภทอื่นมาให้ครบก่อน
