## รันโปรเจกต์

Node.js ติดตั้งไว้ที่ `~/.local/node` แล้ว และเพิ่ม PATH ใน `~/.zshrc` ให้เรียบร้อย

```bash
npm run dev
```

```bash
npm run build
```

## เดโมสำหรับนำเสนอ

**เข้าระบบ** มีสองโหมด แล้วแต่ว่ามีกุญแจ Supabase ใน `.env.local` หรือเปล่า (ดู `lib/cloud.ts`)

| โหมด | ใช้เมื่อไหร่ | การเข้าระบบ |
|---|---|---|
| local / เดโม / GitHub Pages | นำเสนอ ลองฟีเจอร์ | เลือกบทบาทแล้วเข้าเลย — **ล็อกอินปลอม** ไม่แตะเซิร์ฟเวอร์ |
| cloud | ใช้กับเซิร์ฟเวอร์จริง | **อีเมล + รหัสผ่านจริง** (Supabase Auth) แล้วดูตาราง `app_users` ว่าเป็น นศ./อจ. คนไหน |

ยังไม่ได้ต่อ SSO ของมหาวิทยาลัย — ตอนนี้ภาคต้องเชิญผู้ใช้ทีละคน (`0007_invite_admin.sql`)

**สลับบทบาทระหว่างเดโมโดยไม่ต้อง logout**
- ฝั่งนักศึกษา → แตะกระดิ่งมุมขวาบน (หน้า sync) → การ์ด "เครื่องมือสำหรับการนำเสนอ" → **มุมมองอาจารย์**
- ฝั่งอาจารย์ → การ์ดชื่ออาจารย์มุมซ้ายล่าง → **ดูมุมมองนักศึกษา**

**รีเซ็ตข้อมูลกลับสถานะเริ่มต้น** (ก่อนเริ่มเดโมรอบใหม่): หน้า sync → **รีเซ็ตข้อมูล**

**ลำดับที่แนะนำสำหรับ 5 นาที**
1. หน้าแรก → กด "ผ่าน Step" → bottom sheet → ยืนยัน → toast + ปุ่มเลิกทำ (แสดงว่ากดผิดแก้ได้)
2. หน้า sync → เปิดโหมดออฟไลน์ → กลับหน้าแรก → กดผ่าน step อีกครั้ง → ยังสำเร็จทันที + ป้าย "รอ sync"
3. กลับหน้า sync → เห็นคิว → ปิดออฟไลน์ → กด sync ทันที
4. คนไข้ → เปิดเคส → timeline 0–10 พร้อม checklist และ badge "ทำเอง"
5. เกณฑ์ → เกณฑ์สะสม 2 ปี (CD/RPD/Crown+Post-core) และเกณฑ์รายปีแยกกันคนละการ์ด
6. ส่งออก → หน้ารายงาน A4 มีช่องลงนาม → ปุ่มสร้าง PDF (สั่งพิมพ์จริง) / CSV (ดาวน์โหลดจริง)
7. สลับเป็นอาจารย์ (แถบบนสุด) → เมนูซ้ายมี 7 หน้า: ภาพรวม · วิเคราะห์ · ตรวจงานรายคน · ตารางส่งรายงาน · Case CD · เคสค้าง · ตั้งค่าเกณฑ์
8. อาจารย์ → ตรวจงานรายคน (อนุมัติ/ตีกลับ/ตรวจรับเข้าเกณฑ์) → ตั้งค่าเกณฑ์ แล้วกลับไปดูหน้านักศึกษา ตัวเลขเปลี่ยนตามทันที

## กติกาที่ implement ไว้แล้ว

1. **Upper/lower เป็นคู่** — `pairId` + `acceptedDate` เดียวกัน แต่ `procIndex` แยกกันเด็ดขาด
2. **% completed** = `(progression + 1) / (maxProgression + 1)` ตรงกับคอลัมน์ `% Completed` ในชีต
3. **เกณฑ์ขั้นต่ำ (แก้ล่าสุด 2 ก.ย. 2026)** — สะสม 2 ปี: CD 2 (นับต่อ arch) · RPD 2 · Crown/Bridge 2 โดยในนั้นต้องเป็น Post-core อย่างน้อย 1
   (Post-core นับรวมอยู่ในโควตา Crown ไม่ได้แยก) **บวกเงื่อนไขรายปี**: ทุกปีการศึกษาต้องจบอย่างน้อย 3 ชิ้นงาน
   นับเมื่อ `progression === 10` และ `minimumRequirement === true`; Simple APD และ Recall ไม่นับ
   อาจารย์แก้ค่าทั้งหมดได้จาก rail ขวาของหน้าตรวจงาน
4. **ลำดับการแสดงรายการ** — minimum requirement ก่อน → CD → RPD → APD → Post-core → Crown/Bridge → Recall Rem. → Recall Fixed และผู้ป่วยคนเดียวกันอยู่ติดกัน
5. **เคสค้าง** — ไม่อัปเดตเกิน N วัน (ตั้งได้ 7/14/21/30) flag ทั้งสองฝั่ง
6. ~~รอบส่งรายงาน~~ — **ถอดออกแล้ว** (ส.ค. 2569) แทนด้วยเช็คอินรายคาบ · `rounds.ts` ลบทิ้งแล้ว
7. **Export** — PDF ที่มีช่องลงนาม (`window.print()`) และ CSV ตามคอลัมน์ชีตเดิม
8. **Self-performed (`*`)** — เก็บลง `ProgressUpdate.selfPerformed` และมี badge "ทำเอง" ใน UI
9. **Offline-first** — เขียนลง IndexedDB ทันที เข้าคิว แล้ว sync เมื่อออนไลน์
10. **เลิกทำ** — บันทึกเป็น reversal ใน `ProgressUpdate` ไม่ลบประวัติ
11. **Audit log** — ทุกการเปลี่ยน step / อนุมัติ / สร้างชิ้นงาน
12. **Catalog versioning** — ทุกชิ้นงานเก็บ `catalogVersion` (`DTPT502-2569`)
13. **ชนิดชิ้นงานถอดได้ตามชีต** — CD / Complicated APD / Complicated RPD / Simple RPD / Simple APD พร้อมวงเล็บบอกจำนวนฟันที่เหลือ (`domain/catalog.ts → DENTURE_CLASSES`)
14. **Count CDA** — คำนวณอัตโนมัติจากจำนวน arch ที่เป็น CD หรืองาน Complicated แสดงในแท็บ Case CD ของ dashboard
15. **สถานะ “ยังไม่เข้าเกณฑ์ · รอตรวจ”** — ชิ้นงานที่อาจารย์ยังไม่ตรวจรับ จะไม่ถูกนับเข้าเกณฑ์ อาจารย์กดตรวจรับได้จากหน้าตรวจงาน
16. **รายงาน A4 มีช่องติ๊ก 0–10** ครบ 11 ช่องเหมือนชีต · CSV เรียงคอลัมน์ตรงกับ tab PTn รวม Sect II (แยก Removable/Fixed) และวันที่บันทึกข้อมูล
17. ~~ตารางส่งรายงาน 7 รอบ~~ — **ถอดออกพร้อมระบบรายงาน**
18. **กดเลข step 0–10 ที่ไหนก็ได้เพื่อดูว่าข้างในมี procedure อะไร** — กราฟคอขวด (ทั้งหน้าภาพรวมและหน้าวิเคราะห์)
    และ timeline ของนักศึกษา · เลือก "ทุกประเภท" จะเทียบให้เห็นว่า step เดียวกันหมายถึงคนละขั้นตอนในแต่ละประเภทงาน
    (`components/StepInfo.tsx`)
19. **การแสดงผลเลือกตามขนาดข้อมูลจริง** — เกณฑ์เป็นหลักหน่วย (CD 2 · RPD 2 · Crown 2 · ปีละ 3)
    นักศึกษาหนึ่งคนมีเคสไม่ถึงสิบชิ้น จึงตั้งใจ**ไม่**ใช้กราฟที่ทำให้ดูเหมือนมีข้อมูลละเอียดกว่าความจริง:
    - **รายคน** → `RequirementSlots` ช่องทีละเคส (ทึบ = จบแล้ว · อ่อนพร้อมเลข = เคสที่กำลังทำจะมาลงช่องนี้ · ประ = ยังไม่มี)
    - **รายกลุ่ม** → `DivergingBars` ต่างจากค่าเฉลี่ยทั้งชั้นปีกี่จุด + `Heatmap` แท่งเล็กรายคน × เป้าหมาย
    - **คอขวด** → `CaseMap` หนึ่งจุด = ชิ้นงานจริงหนึ่งชิ้น เรียงเป็นกองตาม step (unit chart ไม่ต้องเฉลี่ยอะไรเลย)
    - **ระดับ cohort** (n หลักร้อย) → กราฟปกติใช้ได้: ระยะเวลาต่อประเภท · จบเคสต่อเดือน · funnel
    - `charts/Radar.tsx` เก็บไว้แต่ยังไม่ได้ใช้ — เหตุผลอยู่ในหัวไฟล์
20. **หน้าวิเคราะห์** — คนที่เสี่ยงไม่ทันเกณฑ์ (ประเมินจาก**เคสที่มีอยู่ในมือเดินมาถึงไหน** ไม่ใช่อัตราการจบต่อเดือน
    ซึ่งไม่มีความหมายที่ n หลักหน่วย), จบเคสต่อเดือนตลอดปีการศึกษา, ระยะเวลารับเคส→จบเคสต่อประเภท,
    คอขวดว่าชิ้นงานกองอยู่ที่ step ไหน, funnel อัตราจบเคสต่อประเภท, และ lab step ที่ต้องทำเอง
    ทุกตัวเลขคำนวณสดจากข้อมูลในระบบ ไม่มีค่า hard-code

## ยังไม่ได้ทำ — ต้องคุยกับภาควิชาก่อน

ตรงกับหัวข้อ "ที่ยังไม่ได้ออกแบบ" ใน handoff:

1. **SSO มหาวิทยาลัย** — ตอนนี้ล็อกอินด้วยอีเมล+รหัสผ่านของ Supabase ได้จริงแล้ว และแยก role นศ./อจ./แอดมินแล้ว
   แต่ยังไม่ได้ต่อ SSO มหิดล หรือจำกัดโดเมน Google Workspace — ภาคต้องเชิญผู้ใช้ทีละคนไปก่อน
2. **นำร่องเซิร์ฟเวอร์กลางกับคนจริง** — โครงสร้างทำครบแล้ว: Supabase + local-first sync (`data/cloudSync.ts`),
   RLS ต่อแถว, audit log, migration `0001`–`0014` รันครบแล้ว (8 ก.ย. 69) · **`0017_conflict.sql` ยังไม่ได้รัน**
   **แต่ยังไม่เคยให้ผู้ใช้จริงลองพร้อมกันหลายเครื่อง** — ข้อ 3 ข้างล่างคือสิ่งที่ต้องเคลียร์ก่อนถึงตรงนั้น
   (ข้อ 4 เรื่องชนกันทำเสร็จแล้ว แต่ต้องรัน `0017` ก่อนถึงจะมีผลจริง)
3. **PDPA** — ทำโครงไว้แล้ว แต่ยัง **ปิดอยู่ทุกสวิตช์** จนกว่าคณะจะอนุมัติ (ดูหัวข้อ "PDPA" ข้างล่าง)
   - ✅ audit log แก้/ลบไม่ได้ — ทำตั้งแต่ `0009` (trigger `audit_no_change`) และ `0016` ไม่ได้ไปลดความเข้มลง
   - ✅ สิทธิ์ export ตามบทบาท + ทุกครั้งลง audit ว่าใครดึงอะไรออกไปเมื่อไหร่ (`0016` · `lib/export.ts`)
   - ✅ retention ลบจริงทั้งฝั่งเครื่องและฝั่งเซิร์ฟเวอร์ (`0016` · `repo.ts → purgeExpiredCohorts`)
   - 🟡 การปิดบังชื่อ/HN ในหน้าจอ — เครื่องมือพร้อมแล้ว (`lib/privacy.ts`) แต่ **ยังไม่ได้ต่อเข้าหน้าไหน**
     รอเคาะว่าหน้าไหนควรเห็นอะไร
4. **Conflict resolution** เมื่อ sync ทับกัน — **ทำแล้ว 9 ก.ย. 69** (`0017_conflict.sql` + `data/cloudSync.ts`)
   เดิมทั้งระบบใช้ "คนเขียนทีหลังชนะ" ซึ่งพอสำหรับ pilot คนเดียว แต่ที่ 96 คน + อาจารย์สองท่านต่อ นศ. หนึ่งคน
   มันแปลว่างานของคนหนึ่งหายไปเงียบๆ ไล่ด้วยโพรบสองเครื่องเขียนชนกันแล้วเจอของจริง 6 แบบ
   ตั้งใจ**ไม่**ใช้กลไกเดียวกันหมด — แต่ละแบบเจ็บคนละท่า:

## PDPA — โครงที่พร้อมเปิด (9 ก.ย. 2026)

ระบบนี้ยัง **ไม่เคยรับข้อมูลผู้ป่วยจริง** และคณะยังไม่อนุมัติ
งานรอบนี้คือเตรียมฝั่งโค้ดให้พร้อม ไม่ใช่การเปิดใช้ — **ค่าเริ่มต้นทุกตัวคือปิด**

ทุกอย่างคุมด้วยตารางเดียว: `pdpa_policy` (migration `0016_pdpa.sql` · แถวเดียว `id = 'app'`)
แก้ได้เฉพาะหัวหน้าภาค (`is_admin`) ผ่านแผง "นโยบาย PDPA" ในหน้าตั้งค่าเกณฑ์

| สวิตช์ | ค่าเริ่มต้น | ผลเมื่อยังไม่เปิด |
| --- | --- | --- |
| `export_roles` | `{}` | ปุ่มส่งออกในแอปกดไม่ได้ทุกบทบาท |
| `export_identified_roles` | `{}` | ไฟล์ที่ส่งออกแสดงรหัสเคสแทนชื่อ/HN เสมอ |
| `retention_enabled` | `false` | ลบข้อมูลรุ่นเก่าไม่ได้ แม้แต่หัวหน้าภาค |
| `retention_cohorts` | `5` | (ค่าตั้งต้น ยังไม่ใช่มติภาค) |
| `mask_by_default` | `true` | — ยังไม่มีหน้าไหนอ่านค่านี้ รอเคาะเรื่องหน้าจอก่อน |

### ① ปิดบังชื่อ/HN — เครื่องมือพร้อม ยังไม่ต่อเข้าหน้าจอ

`src/lib/privacy.ts` — `caseCode()` · `maskedName()` · `maskedHn()` · `patientLabel(p, level)`
รหัสเคสคำนวณจาก id ภายในของผู้ป่วย **ไม่ใช่จาก HN** — ถ้าคำนวณจาก HN คนที่รู้ HN ของคนไข้คนหนึ่ง
จะไล่เดาได้ว่าแถวไหนคือคนนั้น (HN เป็นเลขไม่กี่หลัก ทำตารางเทียบได้ในไม่กี่นาที)

⚠️ รหัสเคส **ไม่ใช่ข้อมูลนิรนาม** — มันคือนามแฝง ยังนับเป็นข้อมูลส่วนบุคคลตาม PDPA
ประโยชน์คือลดจำนวนคนที่เห็นชื่อจริงลงเหลือเท่าที่จำเป็น ไม่ใช่ทำให้ข้อมูลหลุดกรอบกฎหมาย

ใช้แล้วเฉพาะ 2 จุด: ไฟล์ที่ส่งออกแบบปิดบัง และข้อความใน audit log (ดูข้อ ④)

### ② Retention — ลบจริงสองฝั่ง

- ฝั่งเซิร์ฟเวอร์: RPC `purge_expired_cohorts('ลบถาวร')` — ลบ 11 ตารางในธุรกรรมเดียว
  ต้องผ่านสองด่าน: คนสั่งเป็นหัวหน้าภาค **และ** `retention_enabled = true`
- ฝั่งเครื่อง: `repo.ts → purgeExpiredCohorts` ลบ IndexedDB ของเครื่องที่กดปุ่ม

**ลำดับสำคัญ**: เซิร์ฟเวอร์ก่อน เครื่องทีหลัง — ถ้าทำกลับกันแล้วเซิร์ฟเวอร์ปฏิเสธ
เครื่องนี้จะว่างแต่ตู้กลางยังเต็ม แล้ว `pullAll` รอบถัดไปดึงกลับลงมาหมด
ผู้ใช้จะเห็นว่า "ลบแล้วมันกลับมา" โดยไม่รู้สาเหตุ

ทำไมพึ่งคิว sync อย่างเดียวไม่พอ — คิวลบได้เฉพาะแถวที่มีอยู่ในเครื่องนั้น และล้มเหลวแบบเงียบได้ 4 ทาง
(เหตุผลเต็มอยู่ในหัวข้อ ⑥ ของ `0016_pdpa.sql`)

**คนที่ไม่มี `entryYear` จะไม่ถูกลบเลย** — เดารุ่นแล้วลบผิดคนคือความเสียหายที่กู้ไม่ได้
หน้าตั้งค่าขึ้นตัวเลขให้เห็นว่ามีค้างกี่คน ต้องไปเติมรุ่นในหน้ารายชื่อก่อน

### ③ สิทธิ์ export

ทุกการส่งออกผ่าน `exportCsv()` ตัวเดียว ซึ่งทำตามลำดับ: ตรวจสิทธิ์ → จด audit ที่เซิร์ฟเวอร์ → ค่อยสร้างไฟล์
จดไม่ผ่าน = ไม่มีไฟล์ · เวลาและตัวตนผู้ทำมาจากเซิร์ฟเวอร์ (`log_export`) ฝั่งแอปปลอมไม่ได้

⚠️ **ขอบเขตที่ทำได้จริง** — นี่คือการคุม "ปุ่มในแอป" ไม่ใช่การคุม "การเอาข้อมูลออก" ทั้งหมด
คนที่เขียนสคริปต์ยิง REST API อ่านแถวเองแล้วประกอบไฟล์เองยังทำได้อยู่
ตัวคุมของกรณีนั้นคือ RLS (`0004`–`0012`) ว่าบัญชีนั้นอ่านแถวไหนได้บ้าง

### ④ audit log ที่แก้ไม่ได้ — มีอยู่แล้วก่อนงานรอบนี้

`0009` ใส่ trigger `audit_no_change` ห้าม UPDATE/DELETE ทุกกรณี และ `audit_stamp_actor`
ประทับ `actor_uid` จากคนที่ล็อกอินเสมอ · `0016` **เพิ่มความเข้ม** อีกชั้น: ช่อง `kind`/`detail`
ที่ client ส่งมาเองถูกล้างเป็น null มีแต่ฟังก์ชันบนเซิร์ฟเวอร์ที่เขียนได้

เพราะแถว audit ลบไม่ได้ จึง **ห้ามใส่ชื่อหรือ HN ผู้ป่วยลงข้อความ audit** —
ไม่งั้นข้อมูลจะอยู่เกินกำหนดเก็บถาวรและลบตาม retention ไม่ได้
จุดเดียวที่เคยใส่ (`updatePatientNote`) เปลี่ยนไปใช้รหัสเคสแล้ว

## ค้างให้ภาควิชา/คณะตัดสิน (PDPA)

เรียงตามลำดับที่ควรถาม — ข้อ 1–3 บล็อกการรับข้อมูลจริง

1. **ระยะเวลาเก็บที่แน่นอน** — ตอนนี้ค่าตั้งต้นคือ 5 รุ่น จาก "ประมาณ 5 ปี" ที่อาจารย์เคยพูด
   ต้องได้ตัวเลขที่เป็นมติ + **นับจากอะไร** (จบการศึกษา? ปิดเคสสุดท้าย? ปีการศึกษาที่รับเข้า?)
   ตอนนี้โค้ดนับจากปีที่ขึ้นคลินิกปีแรก (`entryYear`)
2. **ใบยินยอมผู้ป่วย** — ยังไม่มีเลยในระบบ ทั้งข้อความและช่องเก็บสถานะ
   ต้องรู้ก่อนว่าใครเป็นผู้ควบคุมข้อมูล (คณะ? โรงพยาบาลทันตกรรม?) และใบยินยอมเดิมของคลินิก
   ครอบคลุมการเก็บในระบบนี้อยู่แล้วหรือต้องขอใหม่
3. **ข้อมูลอยู่เซิร์ฟเวอร์สิงคโปร์** — Supabase region ที่ใช้อยู่ไม่ได้อยู่ในไทย
   ต้องให้คณะรับทราบและตัดสิน: ยอมรับได้ / ย้าย region / ย้ายไปเซิร์ฟเวอร์มหาวิทยาลัย
   (ย้าย region = สร้างโปรเจกต์ใหม่แล้ว migrate ทำได้ตอนยังไม่มีข้อมูลจริงเท่านั้น — ตอนนี้คือจังหวะที่ถูก)
4. **หน้าไหนควรเห็นชื่อ/HN บ้าง** — ข้อเสนออยู่ในหัวข้อ PDPA ข้างบน ยังรอเคาะ
5. **audit log เก็บนานแค่ไหน** — ตอนนี้ลบไม่ได้เลยโดยตั้งใจ (เป็นหลักฐาน)
   แต่แถว audit มี **ชื่อนักศึกษา** อยู่ ซึ่งขัดกับ retention ของนักศึกษาเอง
   ถ้าภาคต้องการให้ลบตามไปด้วย ต้องแก้ trigger ใน `0009` — **ยังไม่ทำ** เพราะเป็นการลดความเข้มของสิ่งที่ตั้งใจทำไว้
6. **รูปผู้ป่วย** — ยังอยู่แค่ใน IndexedDB ของเครื่อง ยังไม่ขึ้น storage กลาง
   `purgeExpiredCohorts` ลบ metadata ในตาราง `photos` แล้ว แต่ถ้าวันหน้าขึ้น storage ต้องลบไฟล์จริงด้วย
7. **สิทธิ์ผู้ป่วยตาม PDPA** — ขอดู/ขอแก้/ขอลบข้อมูลตัวเอง ระบบยังไม่มีทางทำเลย
   (ตอนนี้ผู้ป่วยไม่มีบัญชี และไม่มีหน้าให้ภาคค้นแล้วลบรายคน)
8. **ผู้ประมวลผลข้อมูล** — Supabase เป็น data processor ต้องมีสัญญา (DPA) หรือไม่ ตามที่คณะกำหนด

  ผู้ป่วยที่นัด · โน้ต — หน้าแรกมีแบนเนอร์เตือนถ้าวันนี้ยังไม่เช็คอิน
- **อาจารย์** (เมนู "ประเมินรายคาบ"): คิวคาบที่รอประเมิน แยกกลุ่ม — ให้คะแนน 0–3 ทั้ง 8 หัวข้อตาม Part B ของสมุด
  (Knowledge, Skill, Universal Precaution, Instrument Prep, Time Management, Chart Recording, Communication,
  General Conduct) → "บันทึกผล · ลงนาม" เทียบเท่าเซ็นสมุด นักศึกษาเห็นคะแนนทันที
- ระบบรายงาน (S5 + ตารางส่งรายงาน + การ์ดรอบ deadline) ถูกถอดออกทั้งหมด · หน้า export PDF/CSV ยังอยู่ (ลิงก์ท้ายแท็บ "คาบ")
- **รอทำต่อ**: แบบประเมินรวมต่อเคสแยกตามประเภทงาน (Assessment form for Removable prosthesis case ฯลฯ) — ผู้ใช้จะส่งฟอร์มของประเภทอื่นมาให้ครบก่อน
