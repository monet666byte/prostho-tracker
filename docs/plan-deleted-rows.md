# แผน: แถวที่ถูกลบบนเซิร์ฟเวอร์ ต้องหายจากทุกเครื่อง

สถานะ: **ร่างให้เจ้าของโปรเจกต์ตัดสิน — ยังไม่ได้เขียนโค้ดสักบรรทัด**
ที่มา: ข้อจำกัดใน `docs/status.md` ข้อ 7 และคอมเมนต์ที่หัว `pullAllOnce` ใน `src/data/cloudSync.ts`

## ปัญหาเป็นภาษาคน

เวลามีคนลบอะไรสักอย่าง (อาจารย์ลบใบประเมินที่กรอกผิด · นักศึกษาลบคาบที่เช็คอินผิดวัน · หัวหน้ารายวิชาล้างรุ่นที่จบไปแล้ว)
เซิร์ฟเวอร์ลบให้จริง แต่ **เครื่องอื่นที่ปิดแอปหรือไม่มีเน็ตอยู่ในวินาทีนั้นจะไม่มีวันรู้** ว่าของชิ้นนั้นถูกลบไปแล้ว

ผลที่ผู้ใช้เห็น:

1. **ของที่ถูกลบยังโผล่อยู่บนเครื่องนั้นตลอดไป** — เช่นอาจารย์ท่านที่สองยังเห็นใบประเมินที่ท่านแรกลบไปแล้ว ตัวเลขสองเครื่องไม่ตรงกัน
2. **แย่กว่านั้น: ของที่ถูกลบอาจ "ฟื้น" กลับขึ้นเซิร์ฟเวอร์** — ตอนเปิดแอป ตัว `pushAll` ดันแถวที่ "เครื่องมีแต่เซิร์ฟเวอร์ไม่มี" ขึ้นไป
   เพราะมันแยกไม่ออกว่า "แถวนี้ยังไม่เคยขึ้น" กับ "แถวนี้เคยขึ้นแล้วถูกลบ" (ทุกวันนี้รอดเพราะ `serverKeys` ช่วยกรองได้บางจังหวะเท่านั้น)

วันนี้เครื่องที่ **เปิดแอปค้างอยู่และมีเน็ต** ไม่มีปัญหา เพราะ realtime ส่งข่าวการลบมาให้ทันที ปัญหาเกิดกับเครื่องที่ไม่ได้ออนไลน์ตอนนั้น

## เกิดบ่อยแค่ไหน

ไม่บ่อย: การลบในแอปมีไม่กี่จุด (คาบ · ชิ้นงาน · ผู้ป่วย · รูป · ใบ Section II/III · ล้างรุ่นเก่า) และส่วนใหญ่เจ้าของแถวลบของตัวเองบนเครื่องตัวเอง
กรณีที่เจ็บจริงคือ **คนเดียวสองเครื่อง** (ลบบนมือถือ ไอแพดยังเห็น) กับ **อาจารย์หลายท่านดูนักศึกษาคนเดียวกัน**

## ทำไมถึงยังไม่ลงมือ

วิธีแก้ทุกแบบต้องให้แอป **ลบข้อมูลในเครื่องตามคำบอกของเซิร์ฟเวอร์** ซึ่งเป็นการกระทำที่อันตรายที่สุดในระบบนี้ —
ถ้าตรรกะพลาดทางเดียว งานที่นักศึกษายังไม่ได้ส่งจะถูกลบทิ้งเงียบๆ (ตรงกับหัวข้อ "ข้อมูลหาย — ข้อที่แพงที่สุด" ใน `CLAUDE.md`)
จึงควรให้เจ้าของเลือกแนวทางก่อน และทำตอนที่มีเวลาลองใช้จริงหลายวัน ไม่ใช่กลางช่วงนำร่อง

## ทางเลือก

### ก. สมุดจดการลบบนเซิร์ฟเวอร์ (แนะนำ)

- migration ใหม่: ตาราง `deleted_rows (table_name, pk, deleted_at)` + trigger `after delete` บนทุกตารางที่ sync (15 ตาราง) จดลงสมุดอัตโนมัติ
- แอป: ทุกรอบ pull อ่านสมุดเฉพาะบรรทัดใหม่ (`deleted_at >=` ครั้งล่าสุด − 2 นาที แบบเดียวกับ `updated_at`) แล้วลบแถวนั้นในเครื่อง
  **ยกเว้นแถวที่มีงานค้างส่ง / ถูกกัก / กำลังรอลบเอง** (กติกา `skip` เดียวกับ pull)
- `pushAll` เช็คสมุดก่อนดัน: แถวที่อยู่ในสมุด = เคยถูกลบ ห้ามฟื้น
- สมุดเก็บแค่ชื่อตารางกับ id (ไม่มีชื่อ/HN ผู้ป่วย — id ของระบบนี้ไม่ฝังข้อมูลส่วนตัว) · ล้างบรรทัดที่เก่ากว่า 90 วันได้
- RLS: อ่านได้เฉพาะบัญชีที่ผูกแล้ว · เขียนได้เฉพาะ trigger

ข้อดี: ถูกต้องครบ · เบา (อ่านเฉพาะของใหม่) · แก้เรื่อง "ฟื้น" ได้ด้วย
ข้อเสีย: ต้องรัน migration · เครื่องที่ปิดแอปนานเกินอายุสมุด (90 วัน) ยังพลาดได้ → ต้องมีทางเลือก ข. เป็นตาข่ายชั้นสอง

### ข. เทียบรายการตอนดึงทั้งตาราง

ทุกครั้งที่เปิดแอป แอปดึงทั้งตารางอยู่แล้ว (รู้ว่าเซิร์ฟเวอร์มี id อะไรบ้าง → `serverKeys`) จึงลบแถวในเครื่องที่ "ไม่อยู่ในรายการ และไม่มีงานค้างส่ง" ได้เลย ไม่ต้องมี migration

ข้อดี: ไม่แตะเซิร์ฟเวอร์ · ทำได้เร็ว
ข้อเสีย (หนัก): **แยกไม่ออกระหว่าง "ถูกลบ" กับ "มองไม่เห็นแล้วเพราะสิทธิ์เปลี่ยน"** — เช่นอาจารย์เลิกเป็นที่ปรึกษากลุ่ม แถวของกลุ่มนั้นจะหายจากเครื่อง
(ซึ่งจริงๆ ก็ควรหาย แต่ต้องคิดให้ครบ) · และถ้าการดึงได้มาไม่ครบโดยไม่มี error (เช่นเพดาน 1,000 แถวที่เคยเจอ) จะลบของในเครื่องเป็นพันแถว
→ ต้องมีเบรก เช่น "ถ้าจะลบเกิน N% ของตาราง ให้หยุดแล้วรายงานแทน"

### ค. ไม่ทำ — ปล่อยไว้ตามเดิมช่วงนำร่อง

เขียนข้อจำกัดไว้ในเอกสาร (ทำแล้ว) · ถ้าเจอเคสจริง ให้เจ้าตัวออกจากระบบแบบล้างเครื่องแล้วเข้าใหม่ (ดึงทั้งหมดใหม่ = ตรงกับเซิร์ฟเวอร์)

## ข้อเสนอ

**ช่วงนำร่อง: ค.** แล้ว **หลังนำร่องทำ ก. โดยมี ข. แบบมีเบรกเป็นตาข่ายชั้นสอง**

เหตุผล: ช่วงนำร่องควรหยุดแตะเครื่องยนต์ sync (บทเรียนจาก My Clinic — ของที่ไม่ถูกแก้คือของที่นิ่ง) ปัญหานี้เกิดไม่บ่อยและมีทางแก้เฉพาะหน้า
ส่วนความเสี่ยงของการแก้ (ลบงานที่ยังไม่ส่ง) แพงกว่าความเสียหายของการไม่แก้ (เห็นของที่ควรหายไปแล้ว) มาก

## ถ้าตัดสินใจทำ ก. — ลำดับงาน

1. เขียนเทสต์บน Postgres จริงก่อน (`test:sync-pg`): ลบบนเครื่อง A ขณะเครื่อง B ออฟไลน์ → B เปิดมาต้องหาย · B มีงานค้างบนแถวนั้น → **ห้ามหาย** และต้องขึ้นรายการปัญหา ·
   `pushAll` ต้องไม่ฟื้นแถวที่อยู่ในสมุด
2. migration `00xx_deleted_rows.sql` + `test:rls` (บัญชียังไม่ผูกอ่านสมุดไม่ได้ · client เขียนสมุดเองไม่ได้)
3. โค้ดฝั่งแอปใน `cloudSync.ts` + จุดใส่บั๊กใน `mutate:sync` อย่างน้อย 4 จุด (ลบแถวที่มีงานค้าง · ไม่อ่านสมุด · pushAll ฟื้นของที่ลบ · อ่านสมุดซ้ำทั้งเล่มทุกรอบ)
4. `test:upgrade`: เครื่องรุ่นเก่าที่อัปเดตเป็นรุ่นนี้ต้องไม่ลบอะไรผิดในรอบแรก
5. ลองใช้จริงสองเครื่องอย่างน้อยหนึ่งสัปดาห์ก่อนปล่อย

## คำถามที่ต้องการคำตอบจากเจ้าของ

1. เลือก ก / ข / ค (หรือ ค ตอนนี้แล้ว ก ทีหลัง ตามข้อเสนอ)
2. ถ้าทำ: อายุสมุดจดการลบ 90 วันพอไหม (นักศึกษาที่ไม่เปิดแอปข้ามเทอมจะเกินได้)
