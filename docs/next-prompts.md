# Prompt พร้อมใช้ — งานถัดไปที่โยนให้ Opus ได้

เปิด Claude Code ในโฟลเดอร์ `prostho-tracker` เลือกโมเดล **Opus** แล้ววางทีละก้อน · ทุกก้อนเขียนให้อ่านจบในตัว ไม่ต้องมีบริบทจากแชตเดิม
ก้อนไหนทำเสร็จแล้วลบออกจากไฟล์นี้

กติการ่วมทุกก้อน (อยู่ใน `CLAUDE.md` แล้ว — Opus จะอ่านเอง): ห้าม push · ห้าม `git add -A` · ห้ามแตะเซิร์ฟเวอร์จริง · ข้อความใหม่ห่อ `t()` + เพิ่มใน `i18n.dict.ts` ·
งานที่มีหน้าตาให้ทำ mock ให้เลือกก่อน · แตะ `domain/` หรือ `cloudSync.ts` ต้องรัน `npm test`

---

## 1. ยืนยันจุดใส่บั๊ก M48 (5–10 นาที · ไม่แก้โค้ด)

```
รัน `npx tsx scripts/mutate-sync.mts M48` ในโฟลเดอร์นี้ (ใช้เวลาหลายนาที ระหว่างรันห้ามแตะ src/data/cloudSync.ts เพราะสคริปต์สลับไฟล์นั้นชั่วคราว)
ผลต้องขึ้นว่า "✅ M48 จับได้" — ถ้าขึ้นว่า "รอด" แปลว่าเทสต์ข้อ "อายุของค้างส่งนับจากงานชิ้นแรก" ใน scripts/test-sync-pg.mts ⑧ ยังจับไม่ได้ ให้บอกผมพร้อมสาเหตุ
จบแล้วเช็คว่า `git status` สะอาด (สคริปต์ต้องคืนไฟล์เดิม)
```

## 2. ช่องแจ้งปัญหาในแอป (หมวด ง-B · ต้องมีลิงก์ก่อน)

ต้องเตรียม: ลิงก์ LINE OA หรือ Google Form ที่จะให้ผู้ใช้แจ้งปัญหา

```
เพิ่ม "แจ้งปัญหา / สอบถาม" ในแอป Prostho Tracker ทั้งสองฝั่ง: ฝั่งนักศึกษาเป็นแถวในหน้าตั้งค่า (src/routes/student/Sync.tsx หมวด "บัญชี" หรือหมวดใหม่ "ช่วยเหลือ")
ฝั่งอาจารย์เป็นลิงก์ท้ายแถบเมนูซ้าย (components/teacher/TeacherShell) ลิงก์ปลายทางคือ <วางลิงก์ที่นี่> เปิดแท็บใหม่
ห้ามส่งข้อมูลผู้ป่วยหรือชื่อผู้ใช้ไปกับลิงก์ (ห้ามใส่ query string) · ถ้าโหลดจากโดเมนใหม่ให้เช็ค vite/csp.ts (ลิงก์ออกธรรมดาไม่ต้องแก้ CSP)
ทำ mock เทียบ 2 ตำแหน่งให้ผมเลือกก่อนลงโค้ด แล้วเช็คที่จอ 375px ว่าไม่ล้น
แรงบันดาลใจ: My Clinic @ DTMU มีลิงก์ LINE OA "รายงานปัญหา/แนะนำ/สอบถามการใช้งาน" ในเมนูช่วยเหลือ
```

## 3. ตรวจซ้ำผลตรวจเส้นทาง sync ที่ยังไม่ได้ยืนยันด้วยตา (อ่านอย่างเดียว)

```
อ่านอย่างเดียว ห้ามแก้ไฟล์ · ตรวจสามข้อนี้ในโค้ด Prostho Tracker แล้วรายงานเป็นภาษาคน พร้อม file:line:
(ก) src/data/settingsSync.ts กับ src/data/pdpaSync.ts — ถ้า session หมดอายุ (PostgREST ตอบรหัส PGRST301) สองทางนี้ทำอะไร ค่าที่อาจารย์ตั้งหายไหม
    (cloudSync.ts จัดการแล้วผ่าน isAuthLost/syncStatus แต่สองไฟล์นี้มีทางส่งของตัวเอง)
(ข) src/data/photoStore.ts — รูปที่อัปไม่ขึ้นเพราะ session หมดอายุ ถูกนับเป็น "ถาวร" แล้วเลิกลองไหม หรือรอได้ถูกต้อง
(ค) หน้า Login (src/routes/Login.tsx) — หลังกด "เข้าสู่ระบบอีกครั้ง" (signOutToReLogin ใน store/app.ts) ถ้าคนที่ล็อกอินเข้ามาเป็น "คนละบัญชี" งานค้างของคนเดิมถูกกันไว้จริงไหม (foreignPendingCount)
ข้อไหนเป็นรูจริง ให้เสนอวิธีแก้ + เทสต์ที่ควรเขียน แต่ยังไม่ต้องลงมือ
```

## 4. โหมดลองเล่นแยกจากข้อมูลจริง (หมวด ง-C · งานออกแบบ ยังไม่ลงโค้ด)

```
ออกแบบ (ยังไม่เขียนโค้ด) "โหมดลองเล่น" ให้ Prostho Tracker แบบเดียวกับ Sandbox ของ My Clinic @ DTMU (dtmyclinic.mahidol.ac.th/mc/sandbox/ — แอปทั้งชุดอีกสำเนา ข้อมูลปลอม แถบแดงบนสุดบอกว่ากำลังใช้ Sandbox)
ข้อจำกัดของเรา: ตอนนี้มีเว็บเดโม GitHub Pages (โหมดไม่ต่อ cloud ข้อมูลอยู่ในเครื่อง) กับเว็บนำร่อง Vercel (ข้อมูลจริง) และบัญชี demo@ บนเซิร์ฟเวอร์จริงยังมีสิทธิ์อาจารย์เห็นผู้ป่วยทุกคน (docs/status.md หัวข้อ 3)
อ่าน CLAUDE.md หัวข้อ "ข้อมูลตัวอย่างห้ามแตะเซิร์ฟเวอร์จริง" ก่อน แล้วเสนอ 2–3 ทางเลือก (เช่น: ใช้เว็บเดโมที่มีอยู่เป็น sandbox + ลิงก์จากแอปจริง / โปรเจกต์ Supabase ที่สอง / โหมดในแอป)
เทียบ: ความเสี่ยงข้อมูลปลอมปนของจริง · งานที่ต้องทำ · ค่าใช้จ่าย · ใครดูแล แล้วแนะนำทางเดียว เขียนเป็น docs/plan-sandbox.md แบบเดียวกับ docs/plan-deleted-rows.md
```

## 5. ล็อกขั้นที่อาจารย์เซ็นผ่านแล้วที่ฝั่งเซิร์ฟเวอร์ (หมวด ง-E · สำรวจก่อน)

```
อ่านอย่างเดียวก่อน: ใน Prostho Tracker ตาราง checkins มีกฎเจ้าของช่องฝั่งเซิร์ฟเวอร์แล้ว (supabase/migrations/0020_checkin_field_owner.sql — นักศึกษาแก้คะแนนไม่ได้ อาจารย์แก้โน้ตไม่ได้)
แต่ตาราง workpieces ไม่มี (0020 เขียนเหตุผลไว้บรรทัด 27–32) ช่วยสำรวจว่า: หลังอาจารย์ตรวจงาน/เซ็นผ่าน (ตาราง reviews, ช่อง gates ใน students, สถานะใน workpieces) นักศึกษายังแก้อะไรย้อนหลังได้บ้างผ่าน API ตรง
และควรล็อกอะไรที่เซิร์ฟเวอร์บ้าง (แนวคิดจาก My Clinic: หลังเส้นตาย ข้อมูลแก้ไม่ได้ เจ้าหน้าที่จึงทำงานจากข้อมูลที่นิ่ง)
รายงานเป็นตาราง "ช่อง · ใครแก้ได้ตอนนี้ · ควรเป็นยังไง · ความเสี่ยงถ้าล็อก (sync ของเครื่องออฟไลน์ถูกกักไหม)" ยังไม่ต้องเขียน migration
ข้อควรระวัง: trigger ที่ raise จะทำให้การ sync ของแถวนั้นถูกกักทั้งแถว — 0020/0028 เลือก "คงค่าเดิมเงียบๆ" แทน ให้คิดเรื่องนี้ด้วย
```

## 6. แผนเรื่องแถวที่ถูกลบ (รอเจ้าของตัดสินก่อน)

อ่าน `docs/plan-deleted-rows.md` แล้วเลือก ก/ข/ค · ถ้าเลือก ก:

```
ทำตาม docs/plan-deleted-rows.md ทางเลือก ก (สมุดจดการลบบนเซิร์ฟเวอร์) ตามลำดับงานท้ายไฟล์นั้นเป๊ะๆ: เขียนเทสต์ใน scripts/test-sync-pg.mts ให้ตกก่อน → migration ใหม่เลขถัดไป + test:rls →
โค้ดใน src/data/cloudSync.ts → จุดใส่บั๊กใน scripts/mutate-sync.mts → test:upgrade · กฎเหล็ก: ห้ามลบแถวในเครื่องที่มีงานค้างส่ง/ถูกกัก/รอลบ (ชุด skip เดียวกับ pullAll)
อ่าน CLAUDE.md หัวข้อ "ข้อมูลหาย" ทั้งหัวข้อก่อนเริ่ม · หยุดถามผมก่อนถ้าต้องเปลี่ยนรูปแบบสำเนาคิวบนดิสก์
```

## งานที่ **ไม่ควร** โยนให้โมเดลเล็ก/ทำแบบรีบ

- อะไรก็ตามที่แตะ `src/data/cloudSync.ts` โดยไม่มีเทสต์บน Postgres จริงนำหน้า (ก้อน 6)
- migration ใหม่ทุกไฟล์ — ต้องผ่าน `npm run test:rls` ก่อนส่งให้เจ้าของรัน
