## 0. สิ่งที่รอเจ้าของลงมือ (เรียงตามความสำคัญ)

1. **สำรองข้อมูล** — ยังไม่มีสำเนาเลยตั้งแต่มีข้อมูลผู้ป่วยจริง (หัวข้อ 4) · สร้าง `.env.local` แล้ว `npm run backup` → `npm run restore` (ตรวจสำเนา ไม่ต่อเน็ต)
2. **รัน migration บนเซิร์ฟเวอร์ตามลำดับ `0027` → `0028` → `0029`** (หัวข้อ 2) · ข้อที่แอปรุ่นล่าสุดพึ่ง: `0027` กันลบคาบที่ประเมินแล้ว · `0029` เช็คอินวันละแถว
3. **Push** commit ที่ค้างในเครื่องขึ้น GitHub (Vercel deploy เอง) — ชุดแก้เส้นทางส่งข้อมูล 18–20 ก.ย.
4. **ตัดสิน** แผนเรื่องแถวที่ถูกลบบนเซิร์ฟเวอร์ → `docs/plan-deleted-rows.md` (ข้อเสนอ: ยังไม่ทำช่วงนำร่อง)
5. **ลองหนึ่งครั้งหลัง deploy:** เปิดแอปค้างไว้ แล้ว deploy รุ่นถัดไป → ต้องขึ้นแถบ "มีแอปรุ่นใหม่" (ลองกับ build ในเครื่องแล้วผ่าน · ยังไม่เคยลองบนเว็บจริง)

## 1. เซิร์ฟเวอร์นำร่อง

- **เว็บ:** https://prostho-tracker.vercel.app (Vercel · build จาก branch `main`) · **ฐานข้อมูล:** Supabase (region สิงคโปร์)
- **มีข้อมูลผู้ป่วยจริงได้ตั้งแต่ 14 ก.ย. 2569** — ภาค/คณะอนุญาตให้เก็บช่วงนำร่อง · ทุกสคริปต์ที่ต่อเซิร์ฟเวอร์ต้องคิดว่ากำลังแตะข้อมูลจริง
- **ยังไม่เคยนำร่องกับคนจริงหลายเครื่องพร้อมกัน** — จำลองไว้แล้วใน `npm run test:clinic` (12 เครื่อง + อาจารย์ 2 ท่าน) และ `test:sync-pg`
  แต่คาบจริงที่นักศึกษาทั้งกลุ่มกดพร้อมกันบนไวไฟห้องคลินิกยังไม่เคยเกิด — บั๊กร้ายแรงที่ผ่านมาทุกตัวเจอตอนลองใช้จริง ไม่ใช่ตอนอ่านโค้ด

**วิธีรัน `0027`** (ไฟล์ปิดช่องที่เหลือก่อนส่งมอบ: กันนักศึกษาลบคาบที่ประเมินแล้ว · กฎอ่านต้องเป็นบัญชีที่ผูกแล้ว · index `updated_at` ·
ลบบัญชีทดสอบ `@example.com` · จำกัดขอผูกบัญชี 5 ครั้ง — ไม่ลบข้อมูลผู้ป่วย ไม่แตะบัญชีจริง · รันซ้ำได้)

1. ในเครื่อง: `npm run test:rls` ต้องผ่าน (ชุด ⑮ คือกฎของ 0027 บน Postgres จริงในเครื่อง)
2. Supabase → SQL Editor → วางทั้งไฟล์ `supabase/migrations/0027_handoff_hardening.sql` → Run
3. วาง `supabase/check-migrations.sql` → Run → บรรทัด `0027` ต้องขึ้นว่ารันแล้ว
4. วาง `supabase/security-check.sql` → Run → ต้องไม่มีแถว 🔴
5. แก้ตารางข้างบนในไฟล์นี้

ทุก migration ถัดไปใช้ลำดับเดียวกัน (`CLAUDE.md` หัวข้อ "ความปลอดภัยของฐานข้อมูล")

**SQL ตรวจสอบที่เคยรันแล้วบนเซิร์ฟเวอร์จริง** (อ่านอย่างเดียว รันซ้ำได้ทุกเมื่อ):
`check-step-mismatch.sql` → 0 แถว · `check-demo-actor.sql` → เจอ audit 1 แถวจากวันตั้งต้นระบบ (ไม่มี actor_uid = ไม่ใช่คนจริง) ถือว่าไม่โดน ·
`remove-test-accounts.sql` + `remove-demo-rows.sql` + `check-demo-rows.sql` → รันครบแล้ว ข้อมูลตัวอย่างและบัญชี `@example.com` ถูกลบจากเซิร์ฟเวอร์จริงแล้ว

## 4. สำเนาข้อมูล — ตอนนี้ไม่มีใครรันได้

- สำเนาชุดเดียวที่มีคือ `backups/2026-08-29` (ทำก่อน `backup.ts` จะครอบครบทุกตาราง และก่อนมีข้อมูลจริง) — **โฟลเดอร์ `backups/` อยู่ใน .gitignore**
  จึงอยู่แค่ในเครื่องเจ้าของ
- **เครื่องพัฒนาไม่มี `.env.local`** → `npm run backup` รันไม่ได้ในสภาพปัจจุบัน · ตั้งแต่มีข้อมูลจริง (14 ก.ย.) **ยังไม่มีสำเนาเลย**
- **ต้องมีเจ้าของงานนี้หนึ่งคน:** `<ต้องกรอก: ชื่อผู้รับผิดชอบสำรองข้อมูล>` — สร้าง `.env.local` ตาม `.env.example` (บัญชีหัวหน้ารายวิชา) ·
  รัน `npm run backup` ทุกสัปดาห์ · รัน `npm run restore` (ไม่ใส่ธง = ตรวจสำเนาแบบไม่ต่อเน็ต) ทุกเดือน · เก็บโฟลเดอร์สำเนาในที่ที่ไม่ใช่ GitHub
  วิธีอยู่ใน `docs/dev-setup.md` และ README หัวข้อ "สำรองข้อมูล & กู้กลับ"

## 5. รอภาควิชา/คณะตัดสิน

**PDPA — 8 ข้อ** (รายละเอียดเต็มใน README หัวข้อ "ค้างให้ภาควิชา/คณะตัดสิน (PDPA)") — ข้อ 1–3 ควรได้คำตอบก่อนขยายจากนำร่องเป็นใช้จริง

1. ระยะเวลาเก็บที่แน่นอน (ตอนนี้ 5 รุ่น นับจากปีที่ขึ้นคลินิก — ค่าตั้งต้น ไม่ใช่มติ)
2. ใบยินยอมผู้ป่วย — ยังไม่มีในระบบ · ใครเป็นผู้ควบคุมข้อมูล
3. ข้อมูลอยู่เซิร์ฟเวอร์สิงคโปร์ — ยอมรับ / ย้าย region / ย้ายเข้ามหาวิทยาลัย (ตอนนี้มีข้อมูลจริงแล้ว ย้าย = ต้องกู้สำเนาเข้าโปรเจกต์ใหม่ด้วย `restore.ts`)
4. ~~หน้าไหนเห็นชื่อ/HN~~ — เคาะแล้ว: ตาราง `identityLevelFor` ใน `lib/privacy.ts` · ภาคยังไม่ได้รับรองอย่างเป็นทางการ
5. audit log เก็บนานแค่ไหน (ลบไม่ได้โดยตั้งใจ แต่มีชื่อนักศึกษา)
6. รูปผู้ป่วย — ลบฝั่งเซิร์ฟเวอร์ล้วนอาจเหลือไบต์ค้างใน Storage ต้องรันคำสั่งหาไฟล์กำพร้าท้าย `0018` เป็นระยะ
7. สิทธิ์ผู้ป่วยขอดู/แก้/ลบ — ระบบยังไม่มีทางทำ
8. สัญญาผู้ประมวลผลข้อมูล (DPA) กับ Supabase
   (+ ข้อ 9–10 ใน README: ใครลบบัญชี `auth.users` ของรุ่นที่ถูกลบ · ช่อง "หมายเหตุ" ในไฟล์ปิดบัง)

**ตัดสินแล้ว บันทึกไว้กันคนมาแก้ทีหลัง**
- **รหัสเคสของผู้ป่วยที่นำเข้าจากชีตคำนวณย้อนได้จาก HN — ยอมรับ ไม่เพิ่มค่าสุ่มลับ** (README PDPA ข้อ 11) · เซิร์ฟเวอร์นำร่องมีข้อมูลจริงแล้ว
  **ถ้าวันหน้าจะเปลี่ยนสูตร ต้องเขียน migration ย้าย id ผู้ป่วยทั้งระบบ** ไม่ใช่แค่แก้ฟังก์ชัน
- **สวิตช์ `pdpa_policy.patient_names` ปิด** — นำร่องเก็บแค่ HN ไม่เก็บชื่อผู้ป่วย (`0026`) · เปิดเมื่อภาคสั่ง (ตั้งค่า → นโยบาย PDPA · เฉพาะหัวหน้ารายวิชา)
  ยังไม่มีหน้าให้นักศึกษาเติมชื่อให้เคสเก่าหลังเปิด — ทำตอนจะเปิดจริง

**สมมติฐานที่ยังไม่ยืนยันกับภาค** (ฝังอยู่ในโค้ด แก้ที่จุดเดียว)
- **ปีการศึกษาขึ้นวันที่ 1 มิ.ย.** — `lib/date.ts → academicYear()` และ `current_academic_year()` ใน SQL (`0024`) ต้องแก้คู่กัน · กระทบชั้นปี · รุ่น · การล้างกลุ่มที่ปรึกษา
- **วันสุดท้ายของคลินิก 26 มี.ค.** — `domain/analytics.ts → LAST_CLINIC_DAY` · กระทบตาราง "เสี่ยงไม่ทันเกณฑ์" (คาบที่เหลือ)
- **สูตร Count CDA** และ **คอลัมน์ `for PT502 / for PT602` อยู่แท็บไหนของชีต** (README "ยังไม่ได้ทำ" ข้อ 7)
- **แบบประเมินรวมต่อเคสแยกตามประเภทงาน** — รอฟอร์มของประเภทอื่นจากภาค

## 7. ข้อจำกัดที่รู้ตัวและยังไม่ได้แก้

- เปิดแอปแต่ละครั้งยังดึงทั้งตารางใหม่ (ข้อมูลเต็มปี ≈ 35 MB ต่อการเปิดของเครื่องที่เห็นทุกแถว) — แก้ได้ด้วยจำ `lastPulled` ข้ามการเปิดแอป
  แต่ต้องคิดเรื่อง `pushAll`/`serverKeys` และสิทธิ์ที่เปลี่ยนระหว่างปิดแอปก่อน
- แถวที่ถูกลบบนเซิร์ฟเวอร์ไม่ถูกลบจากเครื่องด้วยรอบ pull (มีแค่ realtime) — เป็นมาแต่เดิม · แผนและทางเลือกอยู่ใน `docs/plan-deleted-rows.md`
- การลบที่ RLS กรองทิ้งเงียบ (ไม่มี error · 0 แถว) แอปยังถือว่าลบสำเร็จ — ตรวจแล้ว (20 ก.ย.) ว่าปุ่มลบทุกปุ่มในแอปมี policy ลบคู่กันบนเซิร์ฟเวอร์ จึงเกิดจากหน้าจอปกติไม่ได้ · ถ้าเพิ่มปุ่มลบใหม่ต้องเช็คข้อนี้
- ยังไม่เคยลองล็อกอิน Google บน iPhone ที่ติดตั้งแอปลงหน้าจอโฮม (อาจกลับมาโผล่ใน Safari แทน)
- หนี้เรื่องขนาดไฟล์ (ไอคอน · service worker แคชทุกก้อน · dexie ก่อนหน้าแรก) — README หัวข้อ "หนี้ทางเทคนิคที่รู้ตัว"
